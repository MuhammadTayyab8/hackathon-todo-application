# Data Model: ChatKit AI Chatbot UI

**Feature**: ChatKit AI Chatbot UI
**Branch**: `001-chatkit-ai-ui`
**Date**: 2026-01-17
**Status**: Phase 1 - Design

## Overview

This document defines the data entities used in the ChatKit AI Chatbot UI feature. These entities represent the frontend data model and correspond to backend entities persisted in the Neon PostgreSQL database.

---

## Entity Definitions

### 1. Conversation

Represents a chat session between a user and the AI assistant.

**Attributes**:

| Field | Type | Required | Description | Validation Rules |
|-------|------|----------|-------------|------------------|
| `id` | string (UUID) | Yes | Unique identifier for the conversation | Must be valid UUID v4 |
| `userId` | string | Yes | ID of the user who owns this conversation | Must match authenticated user |
| `createdAt` | Date | Yes | Timestamp when conversation was created | ISO 8601 format |
| `updatedAt` | Date | Yes | Timestamp when conversation was last updated | ISO 8601 format, >= createdAt |
| `lastMessage` | string | No | Preview of the last message in the conversation | Max 100 characters |
| `messageCount` | number | Yes | Total number of messages in the conversation | >= 0 |

**TypeScript Interface**:
```typescript
interface Conversation {
  id: string;
  userId: string;
  createdAt: Date;
  updatedAt: Date;
  lastMessage?: string;
  messageCount: number;
}
```

**Relationships**:
- One-to-Many with Message (one conversation has many messages)
- Many-to-One with User (many conversations belong to one user)

**State Transitions**:
- Created: When user sends first message without conversation ID
- Updated: When new message is added to conversation
- Accessed: When user loads conversation history

**Business Rules**:
- User can only access their own conversations
- Conversations are never deleted (soft delete if needed in future)
- Conversation ID is generated by backend on creation

---

### 2. Message

Represents a single message in a conversation (from user or AI assistant).

**Attributes**:

| Field | Type | Required | Description | Validation Rules |
|-------|------|----------|-------------|------------------|
| `id` | string (UUID) | Yes | Unique identifier for the message | Must be valid UUID v4 |
| `conversationId` | string (UUID) | Yes | ID of the conversation this message belongs to | Must reference valid conversation |
| `sender` | 'user' \| 'assistant' | Yes | Who sent the message | Must be 'user' or 'assistant' |
| `content` | string | Yes | The message text content | Max 10,000 characters |
| `timestamp` | Date | Yes | When the message was sent | ISO 8601 format |
| `toolCalls` | ToolCall[] | No | Array of tool calls associated with this message | Only present for assistant messages |

**TypeScript Interface**:
```typescript
interface Message {
  id: string;
  conversationId: string;
  sender: 'user' | 'assistant';
  content: string;
  timestamp: Date;
  toolCalls?: ToolCall[];
}
```

**Relationships**:
- Many-to-One with Conversation (many messages belong to one conversation)
- One-to-Many with ToolCall (one message can have many tool calls)

**State Transitions**:
- Created: When user sends message or AI responds
- Displayed: When message is rendered in UI
- Updated: Tool calls may be updated with execution results

**Business Rules**:
- User messages never have tool calls
- Assistant messages may have zero or more tool calls
- Messages are immutable after creation (except tool call status updates)
- Messages are ordered chronologically by timestamp

---

### 3. ToolCall

Represents an action the AI proposes to take on behalf of the user.

**Attributes**:

| Field | Type | Required | Description | Validation Rules |
|-------|------|----------|-------------|------------------|
| `id` | string (UUID) | Yes | Unique identifier for the tool call | Must be valid UUID v4 |
| `messageId` | string (UUID) | Yes | ID of the message this tool call belongs to | Must reference valid message |
| `description` | string | Yes | Human-readable description of what the tool will do | Max 500 characters |
| `parameters` | Record<string, any> | Yes | Parameters for the tool call | Valid JSON object |
| `status` | ToolCallStatus | Yes | Current status of the tool call | See ToolCallStatus enum |
| `result` | string | No | Result of the tool execution (if executed) | Max 1,000 characters |
| `error` | string | No | Error message (if execution failed) | Max 500 characters |

**TypeScript Interface**:
```typescript
type ToolCallStatus = 'pending' | 'approved' | 'rejected' | 'executed' | 'failed';

interface ToolCall {
  id: string;
  messageId: string;
  description: string;
  parameters: Record<string, any>;
  status: ToolCallStatus;
  result?: string;
  error?: string;
}
```

**Relationships**:
- Many-to-One with Message (many tool calls belong to one message)

**State Transitions**:
```
pending → approved → executed (success)
pending → approved → failed (error)
pending → rejected (user rejects)
```

**Business Rules**:
- Tool calls start in 'pending' status
- User must approve before execution
- Rejected tool calls are never executed
- Result is only present if status is 'executed'
- Error is only present if status is 'failed'
- Status transitions are unidirectional (no going back)

---

### 4. User

Represents an authenticated user (managed by Better Auth, referenced in chat context).

**Attributes**:

| Field | Type | Required | Description | Validation Rules |
|-------|------|----------|-------------|------------------|
| `id` | string | Yes | Unique identifier for the user | From Better Auth JWT |
| `email` | string | Yes | User's email address | Valid email format |
| `name` | string | No | User's display name | Max 100 characters |

**TypeScript Interface**:
```typescript
interface User {
  id: string;
  email: string;
  name?: string;
}
```

**Relationships**:
- One-to-Many with Conversation (one user has many conversations)

**Business Rules**:
- User entity is managed by Better Auth
- Chat feature only reads user data, never modifies
- User ID from JWT is used to scope all data access

## API Request/Response Types

### SendMessageRequest

Request payload for sending a message to the chat API.

```typescript
interface SendMessageRequest {
  message: string;
  conversation_id?: string | null;
}
```

**Validation**:
- `message`: Required, 1-10,000 characters
- `conversation_id`: Optional, must be valid UUID if provided, null for new conversation

---

### SendMessageResponse

Response from the chat API after sending a message.

```typescript
interface SendMessageResponse {
  conversation_id: string;
  response: string;
  tool_calls?: ToolCall[];
}
```

**Fields**:
- `conversation_id`: ID of the conversation (new or existing)
- `response`: AI assistant's response text
- `tool_calls`: Array of tool calls proposed by the AI (if any)

---

### GetConversationsResponse

Response from the API when fetching conversation history.

```typescript
interface GetConversationsResponse {
  conversations: Conversation[];
}
```

---

### ToolActionRequest

Request payload for approving/rejecting a tool action.

```typescript
interface ToolActionRequest {
  conversation_id: string;
  tool_call_id: string;
  action: 'approve' | 'reject';
}
```

**Validation**:
- `conversation_id`: Required, must be valid UUID
- `tool_call_id`: Required, must be valid UUID
- `action`: Required, must be 'approve' or 'reject'

---

### ToolActionResponse

Response from the API after tool action approval/rejection.

```typescript
interface ToolActionResponse {
  tool_call_id: string;
  status: 'executed' | 'rejected' | 'failed';
  result?: string;
  error?: string;
}
```

## Frontend State Model

### ChatState

Global state for the chat interface (managed via React Context).

```typescript
interface ChatState {
  // Current conversation
  currentConversationId: string | null;
  messages: Message[];

  // Conversation list
  conversations: Conversation[];

  // UI state
  isLoading: boolean;
  isSending: boolean;
  isLoadingHistory: boolean;

  // Error state
  error: string | null;

  // Unsent message (for retry)
  unsentMessage: string | null;
}
```

## Validation Rules Summary

### Message Content
- Minimum length: 1 character
- Maximum length: 10,000 characters
- No empty or whitespace-only messages
- Special characters and emojis allowed
- Code blocks supported (markdown format)

### Conversation ID
- Must be valid UUID v4 format
- Must belong to authenticated user
- Null/undefined for new conversations

### Tool Call Parameters
- Must be valid JSON object
- No size limit (backend enforces)
- Structure depends on specific tool

### Timestamps
- Must be ISO 8601 format
- Must be valid date/time
- Cannot be in the future
- updatedAt >= createdAt for conversations

## Data Flow Diagrams

### Send Message Flow

```
User Input → Frontend Validation → API Request → Backend Processing
                                                        ↓
User sees message ← UI Update ← State Update ← API Response
```

### Tool Confirmation Flow

```
AI proposes tool → Display confirmation → User approves/rejects
                                                ↓
                                          API Request
                                                ↓
                                          Backend executes
                                                ↓
                                          API Response
                                                ↓
                                          Display result
```

### Load Conversation Flow

```
User selects conversation → API Request → Backend fetches messages
                                                ↓
                                          API Response
                                                ↓
                                          State Update
                                                ↓
                                          UI renders messages
```

## Database Schema (Backend Reference)

**Note**: The following schema is managed by the backend. This is provided for reference only.

```sql
-- Conversations table
CREATE TABLE conversations (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id VARCHAR(255) NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMP NOT NULL DEFAULT NOW(),
  last_message TEXT,
  message_count INTEGER NOT NULL DEFAULT 0,
  FOREIGN KEY (user_id) REFERENCES users(id)
);

-- Messages table
CREATE TABLE messages (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  conversation_id UUID NOT NULL,
  sender VARCHAR(20) NOT NULL CHECK (sender IN ('user', 'assistant')),
  content TEXT NOT NULL,
  timestamp TIMESTAMP NOT NULL DEFAULT NOW(),
  FOREIGN KEY (conversation_id) REFERENCES conversations(id)
);

-- Tool calls table
CREATE TABLE tool_calls (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  message_id UUID NOT NULL,
  description TEXT NOT NULL,
  parameters JSONB NOT NULL,
  status VARCHAR(20) NOT NULL CHECK (status IN ('pending', 'approved', 'rejected', 'executed', 'failed')),
  result TEXT,
  error TEXT,
  FOREIGN KEY (message_id) REFERENCES messages(id)
);

-- Indexes
CREATE INDEX idx_conversations_user_id ON conversations(user_id);
CREATE INDEX idx_conversations_updated_at ON conversations(updated_at DESC);
CREATE INDEX idx_messages_conversation_id ON messages(conversation_id);
CREATE INDEX idx_messages_timestamp ON messages(timestamp);
CREATE INDEX idx_tool_calls_message_id ON tool_calls(message_id);
```
